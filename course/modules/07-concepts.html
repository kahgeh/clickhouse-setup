Concepts

The ideas behind the platform: how a queue on object storage stays consistent, why a retried insert does not create duplicates, and how to read cumulative metrics.

After this module you can

  • explain how an object-storage queue stays consistent when two writers update its manifest,
  • explain why a retried insert does not create duplicate rows, and
  • read cumulative metrics correctly, including the HyperDX quirks.

OTLP

OTLP (the OpenTelemetry Protocol) is the wire format that applications use to send logs, metrics and traces. The test application in this stack sends OTLP to the collector, which listens on port 4317 for gRPC and port 4318 for HTTP (stack/config/otel-collector.yaml). Every request carries resource attributes such as service.name, so the collector and the tables know which service produced a record.

The three signals travel through separate pipelines in the collector. After the collector, the data is no longer OTLP on the wire: it is written as objects in the Buffer, and the ingestors decode it again before inserting rows.

An object-storage queue and its manifest

The Buffer is a queue made of objects in an S3 bucket. A collector writes each batch as a data object and records it in a manifest, one small object per signal (otel/logs/manifest for logs). A reader sees only the batches the manifest lists, so a data object that is not yet listed is invisible to ingestors.

The risk is two writers updating the manifest at the same moment. Take two collector replicas, A and B, both writing the logs queue. Both read the manifest at version 12, which lists batches up to number 40. A adds batch 41 and B adds batch 42. If each simply overwrote the manifest, the second write would erase the first writer's entry, and batch 41 would be orphaned in the bucket.

The manifest is therefore updated with compare-and-set: a conditional S3 write that succeeds only if the object is still the version the writer read. The stack needs an object store with S3 conditional writes for this, which RustFS and AWS S3 provide (stack/README.md).

The loser re-reads the current manifest, adds its entry on top of it, and tries again. Neither writer needs a lock, and no entry is lost. Ingestors read the manifest the same way, so they never see a half-written list.

At-least-once, exactly-once and effectively-once

A sender that is unsure whether a message arrived can either send it again or give up. Resending guarantees at-least-once delivery: nothing is lost, and some messages may arrive twice. Delivering each message exactly once is not something a network call can promise on its own, because a lost acknowledgement looks the same as a lost request.

The stack uses at-least-once delivery and removes the repeats at the end, so the stored result is the same as if each record had arrived once. This is effectively-once storage, built from idempotent writes: writing the same thing twice has the same effect as writing it once.

HopDeliveryWhat removes or prevents repeats
Application to collectorAt-least-onceNothing. A retry after a lost acknowledgement can duplicate a request's telemetry.
Collector to BufferRetried up to 5 minutes by defaultA batch is reported exported only after the Buffer write is durable.
Buffer to ingestorAt-least-onceAn ingestor acknowledges a range only after ClickHouse accepts it, so a crash replays the range.
Ingestor to ClickHouseEffectively-onceInsert token, then the sort key on merge.

The first hop is the exception. Duplicates created between the application and the collector are not removed by the token, because they enter the pipeline as separate records. Module 11 lists this with the other limits.

The deterministic insert token

Each chunk that an ingestor sends to ClickHouse carries a token built from where its rows came from and how they were cut. For the logs table the token has this form, and a constructed example follows it:

{manifest}:{db}.{table}:{low}-{high}:{adapter_version}:{fingerprint}:{chunk_index}
otel/logs/manifest:otel.otel_logs:17-17:1:<fingerprint>:0
PartExampleMeaning
{manifest}otel/logs/manifestWhich queue the rows came from.
{db}.{table}otel.otel_logsThe destination table.
{low}-{high}17-17The range of queue sequence numbers in the commit group.
{adapter_version}1The adapter version from the ingestor configuration.
{fingerprint}a hashA stable hash of every setting that affects chunk boundaries: database, table, max_chunk_rows, max_chunk_bytes and adapter version.
{chunk_index}0The position of this chunk when a range is split into several inserts.

The token must be identical on a replay because ClickHouse recognises a repeat only by comparing tokens. After a crash the ingestor reads the same range again. The chunk planner sorts the records by sequence, entry and record index, and cuts them at the configured row and byte limits, so the same input gives the same chunks and the same token. ClickHouse has already accepted that token and drops the insert.

A configuration change must change the token. If max_chunk_rows went from 10,000 to 5,000 between a crash and the replay, chunk 0 would hold different rows than before. Reusing its old token would make ClickHouse drop rows it never stored. The fingerprint changes with the setting, so the replay gets new tokens, ClickHouse accepts the inserts, and the sort key (next section) removes the repeats.

ReplacingMergeTree and FINAL

The token check is the first defence and works at insert time, inside ClickHouse's deduplication window (non_replicated_deduplication_window = 1000 in the tables). The second is the table engine. Every table is a ReplacingMergeTree whose ORDER BY ends with the provenance key _odb_sequence, _odb_entry_index, _odb_record_index. Rows that share a sort key are the same record read twice, and a background merge keeps one of them.

Merges run when ClickHouse decides, so until one happens a table can hold both copies. SELECT count() FROM otel.otel_logs FINAL collapses rows with the same sort key while reading, and gives the deduplicated count immediately. The verification checks compare the raw count, the FINAL count and the number of unique provenance keys, and require all three to be equal.

The probe scenario_dedup_token in stack/verify/chaos.py works on a scratch table and asserts two things. Inserting the same chunk twice with the same token must leave 2 rows, because the second insert is dropped. Inserting identical content under a new token must store 4 raw rows, and FINAL must show 2. Its output is not part of the captured evidence here, so run it to see the result.

Cumulative and delta metrics

A counter such as app.requests can be reported in two ways. A cumulative metric reports the total since the process started, and each export repeats the running total. A delta metric reports only the change during the export interval. The test application exports cumulative metrics every 5 seconds, so the stored rows in otel_metrics_sum are running totals and not per-interval counts.

Suppose a counter is exported as 10, 14, 14 and 20. Adding those values gives 58, which is meaningless. The increase is the change between snapshots: 4, 0 and 6, a total of 10 after the first snapshot. The first snapshot cannot give a change because it has nothing before it, which is why charting tools handle it specially. The numbers here are an illustration, not measured values.

HyperDX has three behaviours to know when reading cumulative metrics:

  • Cumulative metric charts drop each series' first point, so the increase before the first snapshot of a series is not shown.
  • Histogram counts are computed from changes between snapshots.
  • As a result the app.requests by outcome dashboard tile undercounts. The verification checks read the final cumulative value of each series instead, which carries the total.

The practical rule is to read the latest value of a cumulative counter, or use a rate over time, and never to add its raw values together. The same applies to a histogram's count and sum.
