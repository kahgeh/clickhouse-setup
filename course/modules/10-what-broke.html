Running it · module 4 of 5

What broke and what we learned

Seven failures found while building the platform, the evidence for each, and the check that would have caught it sooner.

After this module you can

  • recognise the failure patterns found while building,
  • apply the checks that would have caught them, and
  • separate vendor claims from verified behaviour.

War stories

Seven things went wrong while the platform was built, and most were found by a deliberate check and not by luck. Every story below gives what happened, the evidence where there is a captured one, and the lesson. The two log excerpts were reproduced from the unpatched upstream collector image and were captured on 2026-10-03.

1. The documentation said traces were supported

The vendor's documentation described traces as a supported signal for the object-storage exporter. The shipped collector image rejected a traces pipeline when it was validated:

$ otelcol-opendata validate  # upstream image ghcr.io/opendata-oss/otel-collector:v0.4.0, pipeline: traces -> opendata exporter
Error: failed to build pipelines: failed to create "opendata" exporter for data type "traces": telemetry type is not supported

Source: evidence/war-traces-unsupported.txt, upstream image ghcr.io/opendata-oss/otel-collector:v0.4.0. The traces signal was then added in a local patch to the exporter.

Lesson. Verify a claim against the artifact you will run. Documentation, release notes and descriptions state intent, and only running the image shows what it does.

2. Data dropped when the object store stopped

The upstream exporter had no retry. While the object store was stopped for about 9 seconds during a send of 300 log records, each failed write was logged and the batch was discarded:

# upstream collector image, object store stopped for ~9 s while 300 log records were sent
2026-10-03T11:46:36.518Z  error  Exporting failed. Dropping data.  dropped_items=100
    storage error: operation error S3: PutObject, https response error StatusCode: 0, RequestID: , HostID: , request send failed, Put \
2026-10-03T11:46:36.518Z  error  Exporting failed. Dropping data.  dropped_items=100
    storage error: operation error S3: PutObject, https response error StatusCode: 0, RequestID: , HostID: , request send failed, Put \
2026-10-03T11:46:36.518Z  error  Exporting failed. Dropping data.  dropped_items=100
    storage error: operation error S3: PutObject, https response error StatusCode: 0, RequestID: , HostID: , request send failed, Put \

Source: evidence/war-no-retry.txt, same upstream image. 3 batches of 100 items were dropped, which is the 300 records. The long storage-error lines are cut off in the capture.

The exporter's per-call ceiling is 5 seconds by default, and crossing it cancels the call and drops the batch. The producer underneath retries inside that call, so a short outage can be absorbed, and a stop of 9 seconds was not. The 9-second capture is the evidence kept here. A local patch adds retry_on_failure, on by default, and the failure tests now pass with the object store stopped for 8 s and for 30 s under load.

Lesson. Inject faults early. A system that passes while everything is healthy has not yet been asked to do the thing it exists for, and a short fault can hide a gap that a longer one exposes.

3. "Above" meant "at least"

The alerts were set to fire above 4 failures a minute. HyperDX's above means greater than or equal to, so exactly 4 failures fired it, and above_exclusive means greater than. The boundary probe in alerts.py sends exactly 4 failures and requires the alerts to stay quiet. The alerts now use the exclusive form, and a negative test with the old comparison makes the probe fail. The firing messages differ: "N exceeds 4" for exclusive, "N meets or exceeds 4" for inclusive.

Lesson. Test the boundary. A burst far above a threshold passes under any comparison, and only the value on the threshold tells them apart.

4. A test suite that could not fail

A suite of passing checks had never been shown to detect a fault. The self-test damages stored data in 8 ways and requires the right checks to fail each time. It found three defects in the verifier: an early exit that hid other checks, a crash masked by a stale report, and a reused run id (next story). Module 9 shows the results.

Lesson. Test the tests with negative cases, and treat a suite that has only ever passed as unproven.

5. Reused run ids tripled the counts

Checks count rows by run id. Reusing an id meant earlier data was counted again, and every count silently tripled. verify.py now checks first and exits with a message that the run id already has spans and that run ids must be unique, so the cause is named before any count is compared.

Lesson. Make tests refuse unsafe preconditions. A wrong count that looks like a pipeline fault wastes the time of whoever investigates it.

6. The image registry removed the object store

The first local object store was MinIO. Its public images were removed in 2026, and the stack moved to RustFS, which also provides the S3 conditional writes that the Buffer's manifest depends on. The compose file records the reason next to the image.

Lesson. Pin what you depend on, keep a copy you control, and test a fallback that meets the same requirements before you need it.

7. The dashboard drew empty buckets as 0% availability

Every number behind the availability tile was verified through HyperDX's API. Rendering the dashboard in headless Chrome and looking at it showed time buckets with no requests drawn as 0% availability. The query was right and the picture was wrong. The fix was fillNulls: false on the tile, and only the main dashboard has been inspected this way so far.

Lesson. Look at the rendered result as well as the numbers. A correct query can still draw something misleading.

The pattern. Several of these were found by a check designed to fail: a fault injection, a boundary value, a corrupted dataset or a closer look at a rendered chart. The exception is the removed image, which was found when a pull failed.
