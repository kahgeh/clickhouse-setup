Ground truth

A test of a telemetry pipeline needs to know what should have arrived, and it cannot learn that from the pipeline. The load generator sends a fixed request mix to the test application and records, for each endpoint, how many requests it sent, the status it expects, and the exact number of spans and log lines each request must produce. This record is the ground truth, and the checks compare ClickHouse and HyperDX with it.

The numbers are exact, so a single lost span or an extra log line fails a check. They are known without reading telemetry: /chain produces 4 spans and 2 logs by construction, and the generator counts how many times it called it. If the checks derived expectations from ClickHouse, a pipeline that dropped 5% of the data would still agree with itself.

The pipeline checks compare counts per service, severity, span kind and route with the ground truth. The duplicate checks require the raw row count, the FINAL row count and the number of unique provenance keys to be equal, which is how module 7's deduplication is tested. The HyperDX checks ask HyperDX's own API, so they test what a user would see and not only what is stored.

Testing the tests

A check that has only ever passed has not been shown to detect anything. The self-test, stack/verify/selftest.py, runs a clean verification, then deliberately damages the stored data and requires the right checks to fail. All 8 corruptions were detected.

Source: evidence/selftest.json, captured 2026-10-03T14:20:33Z. Every check in the "Must fail" column also appears in "Failed", and other checks failed too.

Negative testing found three defects in the verifier itself, each a way for the suite to report success when it should not have. They are lessons for any test suite:

  • An early exit hid other checks. The run stopped at the first failure, so later checks never ran and a broken run looked narrower than it was. Run every check and report all results.
  • A crash was masked by a stale report. When the verifier crashed, an older report was still on disk and was read as the result. A run must clear or ignore any output it did not produce.
  • Reusing a run id silently tripled every count. Data from earlier runs with the same id was counted again. A test must refuse to start when its precondition is unsafe, and module 10 comes back to this.

Failure injection

The failure tests in stack/verify/chaos.py send load, break one component part-way through, wait for the system to settle, and run the same count and duplicate checks. A failure that loses or repeats data fails them.

Source: evidence/chaos.json, captured 2026-10-03T14:20:33Z.

Replays depend on timing. Killing an ingestor only causes a replay if the kill lands between an insert and its acknowledgement. In the three attempts captured for this course ClickHouse dropped 1, 0, 0 replayed inserts (the count varies from run to run). Every attempt ended with exact counts, so the evidence is that nothing was lost or duplicated, and a single run may see no replay at all.

Data-flow explorer

The explorer is a model of the pipeline, with one step representing one second and the applications producing 10 rows a second. In a healthy run the ingestor empties the queue within the same second, so the queue reads 0 now while the running total under Buffer shows how many rows have been written to it. Stop the ingestor, step time, and watch the queue build up; stop another stage and watch where the rows wait. The behaviour follows the documented design and the failure tests above. The rates are illustrative, and the model does not call any real service.

The collector crash is a real loss. The collector acknowledges the application before a batch reaches the Buffer, so what it holds in memory when it dies is gone. Module 11 lists this with the other open limits. Without JavaScript, the table above describes each fault.
