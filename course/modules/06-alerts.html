The two alerts

This module explains when the platform's two alerts fire, why exactly four failures does not fire them, and what an alert evaluation cannot see. Both alerts watch for more than four failures in one minute. One counts failed requests on a dashboard tile and the other counts ERROR log lines in a saved search.

  • 5xx errors above 4 per minute (dashboard tile) watches the tile Errors (5xx) of the Availability & Latency dashboard, which counts server spans of web with error status (module 5).
  • ERROR logs above 4 per minute (saved search) watches the saved search Error list: error logs, which counts log lines with severity ERROR.

The alerts are created from code through HyperDX's API when the stack is provisioned, like the dashboards. Both use a threshold of 4, the type above_exclusive, an interval of one minute, and one webhook channel that posts to a small local receiver. The receiver records each notification, which is how the tests check deliveries.

Threshold semantics

HyperDX has two threshold types, and the names are easy to misread.

Threshold typeFires whenMessage reads
abovecount ≥ threshold"N meets or exceeds 4"
above_exclusivecount > threshold"N exceeds 4"

The alerts here use above_exclusive and are named "above 4", so a count of exactly 4 does not fire them and a count of 5 does. The alerts page shows "above (>) 4". A request that fails does not always add one to the count, because the two alerts count different things. A /chain-fail request is one 5xx server span, but it writes two ERROR log lines, one from each service, so the log alert counts it twice. Four /chain-fail requests are four failures for the tile and eight lines for the log alert.

When the evaluation happens

HyperDX evaluates each alert once a minute, at second :00, over the minute that just ended. The window is a fixed minute, for example 9:56:00 to 9:57:00 UTC, and not a sliding one. The evaluation does not wait for slow data: a row counts only if it is already in ClickHouse at that moment, and a row that arrives after :00 is not counted by this evaluation or by any later one, because the next evaluation looks at the next minute.

That is the late-row blind spot. The platform's measured delay from event to queryable, for every row of the verification run, was a median of 0.6 s and a 99th percentile of 1.4 s for logs, and a median of 1.2 s and a 99th percentile of 2.8 s for spans. A failure in the last few seconds of a minute can therefore be queryable only after :00. These numbers were measured on one laptop with a 100 ms collector flush; no measurement shows how often a real alert missed rows, and the simulator below takes the delay as an input.

Two consequences follow. Failures spread across two minutes are counted separately, so three failures at the end of one minute and three at the start of the next are not six failures in one window. And the test that checks the boundary starts its burst early in a minute, between second 5 and second 40, so that every row has landed before :00.

The notifications

When an alert changes to ALERT, HyperDX posts to the webhook, and it posts again when the alert returns to OK. The receiver stores the body, which is built from a template with the fields title, state, body and link. These are real deliveries recorded by the receiver during the alert tests. The sample log lines that the log alert appends to its message, and the links, are left out.

How the tests verified it

The alert test sends known traffic and reads the alert states from HyperDX and the notifications from the receiver. It waits for the evaluation, and it checks the boundary that matters: exactly four failures must not fire.

AL0baseline: both alerts reach state OKpass
AL1ahealthy traffic: both alerts remain OKpass
AL1bhealthy traffic: no webhook deliveredpass
AL1cexactly 4 failures (== threshold, not more): both alerts stay OKpass

AL2bfailure burst: a firing (ALERT) webhook delivery arrived for each alertpass

The boundary check is the one that can fail for the right reason. With the wrong threshold type, exactly four failures would send a notification and the check that no notification arrived would fail. The suite was also checked against deliberately wrong alert settings (unreachable thresholds and the >= type), according to the project notes. Those runs are not part of the captured report, so this page does not show them.

What an alert evaluation cannot see

  • Rows that arrive after :00. They are not counted by any evaluation, so a burst at the end of a minute can pass unnoticed.
  • Failures split across windows. The windows are fixed minutes, so the count resets at every :00.
  • Anything the query does not count. The tile alert counts server spans of web with error status, and the log alert counts ERROR lines. A slow response with status 200 is neither.
  • A failed notification. The tests check that the receiver got the posts. They do not show what happens if a real destination is unreachable.

Open limit. The blind spot for late rows is a property of how HyperDX evaluates, observed and documented in this project, and it is listed with the other limits in module 11. If alerts must not miss late data, the alert query or the window needs a delay allowance that this setup does not have.
