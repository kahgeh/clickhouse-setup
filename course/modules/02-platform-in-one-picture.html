The platform in one picture

How telemetry travels from an application to a dashboard, which stage holds it at each moment, and what each stage does when it fails.

After this module you can

  • trace one request from the application to a query in HyperDX,
  • say where data is durable at each step, and
  • predict where data waits when one stage is down.

One request, end to end

Take a request to the web service at /chain. It calls the backend over gRPC and returns 200. Each service reports what it saw to the collector over OTLP. For this request that is four spans and two log lines in total: the web server span and its client span, then the backend server span and an internal span. The response carries the trace identifier in an x-trace-id header, so you can look the request up afterwards.

Each service then sends what it saw to the collector, which batches it and writes each batch to the Buffer, a durable queue on S3. The collector reports a batch as exported only after the Buffer write is durable.

An ingestor then reads the batch from the Buffer, inserts it into ClickHouse, and acknowledges the range afterwards. HyperDX queries ClickHouse separately, with a read-only user.

One of the queries HyperDX sent while drawing the dashboard, read from ClickHouse's query log. It is plain SQL over the same tables, run as the read-only user. The heading line shows how many rows and bytes the query read.

## latency percentile tile: 4 ms, read 25564 rows, 460152 bytes
SELECT quantileIf(0.5)(toFloat64OrDefault(toString(Duration / 1000000)), ((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')) AND (toFloat64OrDefault(toString(Duration / 1000000)) IS NOT NULL)) AS `p50 ms`, quantileIf(0.95)(toFloat64OrDefault(toString(Duration / 1000000)), ((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')) AND (toFloat64OrDefault(toString(Duration / 1000000)) IS NOT NULL)) AS `p95 ms`, quantileIf(0.99)(toFloat64OrDefault(toString(Duration / 1000000)), ((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')) AND (toFloat64OrDefault(toString(Duration / 1000000)) IS NOT NULL)) AS `p99 ms`, toStartOfInterval(toDateTime(Timestamp), toIntervalMinute(1)) AS __hdx_time_bucket
  FROM otel.otel_traces
  WHERE ((Timestamp >= fromUnixTimestamp64Milli(_CAST(1791026220000, 'Int64'))) AND (Timestamp < fromUnixTimestamp64Milli(_CAST(1791028980000, 'Int64')))) AND (((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')) OR ((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')) OR ((SpanKind ILIKE '%Server%') AND (ServiceName ILIKE '%web%')))
  GROUP BY __hdx_time_bucket ORDER BY __hdx_time_bucket ASC LIMIT _CAST(100000, 'Int32') FORMAT JSON

Three signals, three queues

Logs, metrics and traces do not share a queue. Each signal has its own pipeline in the collector, its own manifest in the Buffer, its own ingestor process, and its own ClickHouse tables.

SignalBuffer manifestClickHouse tables
Logsotel/logs/manifestotel_logs
Tracesotel/traces/manifestotel_traces
Metricsotel/metrics/manifestotel_metrics_gauge, otel_metrics_sum, otel_metrics_histogram

Consequence. A problem with one signal, such as an ingestor that cannot decode an entry, stays in that signal's queue and does not stall the other two.
