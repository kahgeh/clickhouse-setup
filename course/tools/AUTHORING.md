# Authoring guide for course modules

Read this fully before writing a module. The finished examples are `modules/01-problem-and-outcome.html`,
`modules/02-platform-in-one-picture.html` and `modules/03-evidence-it-works.html`, built by
`tools/build-module01.py`, `build-module02.py` and `build-module03.py`. Copy their structure and register.

## Hard rules (the user's instructions and the skill's rules)

1. **Banned subject.** The check-course.py banned-term rule lists it. Talk about query volume, never who or what issues queries.
2. **Do not change** `stack/`, `ingest/`, `collector/`, `app/`, `cost/`, `tasks/`, `evidence/`, or the shared sheets `assets/tokens.css`, `theme.css`, `components.css`, `quiz.js`, `mermaid*`. Only add: your `tools/build-moduleNN.py`, your `modules/NN-*.html`, and your own `assets/sim-<name>.js`. Add rules to `assets/local.css` only by appending a clearly commented block, tokens only.
3. **Honest claims.** Say what was measured, what is modelled, what is assumed. Never write "ten times cheaper", never imply AWS or production-volume testing happened (it did not). The cost figures are a model with assumptions. If you cite a number, take it from an evidence file or from `README`/`tasks` facts below, never invent one.
4. The figures from the user's AWS bill are sensitive: no raw screenshot, no internal names, and keep the "sensitive figures" caveat wherever the bill appears.
5. Plain technical-documentation prose: direct, declarative, no suspense or rhetorical setup. The first sentence of a page says what it explains. Headings are short noun phrases specific to the topic. Name the concrete example before the term; mark a defined term with `<dfn>`.
6. Colour and fonts come only from the shared sheets (tokens). No inline `style=` attributes, no raw colours, no inline `<script>`. Interactive code lives in a shared file `assets/sim-<name>.js` linked from the page. Every interactive must work with keyboard, show its result in text (not colour alone), and degrade gracefully if JS fails (the explanation must still be readable).

## Build pattern

```python
#!/usr/bin/env python3
from lib import page, quiz, write, neighbours, evidence, esc     # tools/lib.py
body = f"""  <section aria-labelledby="x"> <h2 id="x">...</h2> ... </section>"""
q = quiz([{"q": "...", "options": [("text", "why"), ...], "answer": 1}, ...], gate="All correct. Continue to module N, ...")
prev, nxt = neighbours("m04")
write("04-sending-telemetry.html", page("04-sending-telemetry.html", "m04", "Title", "Using it", "1 of 3",
      "lede sentence", ["goal 1", "goal 2", "goal 3"], body, q, scripts=["sim-trace.js"], mermaid=False, prev=prev, next=nxt))
```
Run from `course/` as `python3 tools/build-module04.py`. Module ids and filenames are in `lib.ORDER`. The track label is "Using it" for modules 4-6 (numbers "1 of 3", "2 of 3", "3 of 3") and "Running it" for 7-11 ("1 of 5" ... "5 of 5").
Generated numbers and tables come from `evidence/*.json` via `evidence()`: never retype a measured value.

Each module: `.goals` (3 outcomes), body sections (concrete example first), at least one **interactive** and one **evidence** element where the module list below says so, then a quiz of 3 questions.

## Quiz rules (checked by a script)

Three or four options, exactly one right, put the right answer in different positions across questions. Ask for a consequence, mechanism or prediction on a concrete case, never "which is true". Each wrong option is a plausible mistake and its `why` names the mistake and the idea to revisit without stating the right answer; start a `why` with the reason itself (the page already prefixes "Correct." / "Not quite."). The right option must not repeat a sentence from the page: it states a consequence or application the page implied. No hint in the question. Test what the module's goals say.

## Facts bank (verified in this project; use these, do not guess others)

**Architecture.** Apps -> OpenTelemetry collector (one pipeline per signal) -> OpenData Buffer (durable queue of objects on S3; a manifest per signal updated with compare-and-set) -> ingestors (one process per signal) -> ClickHouse <- HyperDX. Manifests: `otel/logs|traces|metrics/manifest`. Tables: `otel_logs`, `otel_traces`, `otel_metrics_gauge|sum|histogram` shaped like HyperDX's default (ClickStack) schema plus provenance columns `_odb_sequence`, `_odb_entry_index`, `_odb_record_index`, `_odb_manifest_path`, `_odb_data_path`, `_odb_ingestion_time_ms`, `_adapter_version`, and `_odb_clickhouse_inserted_at DEFAULT now64(9)` on logs and traces. Engine `ReplacingMergeTree(_adapter_version)`, provenance key in `ORDER BY`, `non_replicated_deduplication_window = 1000`, TTL 30 days. Read-only user `hyperdx_ro` for HyperDX. Local object store is RustFS (MinIO's images were removed in 2026). Collector: the OpenData exporter v0.5.0 with two local patches (traces signal; `retry_on_failure`), built from `collector/`. Ingestors: vendored opendata-contrib with decoders/adapters for traces and metrics added, a `signal:` config, config via YAML plus `INGESTOR__*` environment variables. A malformed (non-protobuf) entry is counted (`ingestor_decode_malformed_entries_total{signal}`) and skipped; a wrong-signal envelope stays fatal. Summary and exponential-histogram metrics are counted in `ingestor_decode_skipped_points_total` and not stored.
**Delivery semantics.** App->collector is at-least-once (a retry after a lost ack can duplicate). The collector reports a batch exported only after the Buffer write is durable; batches in its memory (batch processor, sending queue) are lost if it crashes. Collector->Buffer retries up to 5 min by default. Ingestor->ClickHouse: each chunk has token `{manifest}:{db}.{table}:{low}-{high}:{adapter_version}:{fingerprint}:{chunk_index}`; same token = dropped (insert-time dedup, proved by a probe); `ReplacingMergeTree` collapses rows with the same sort key on merge (`FINAL` shows the collapsed view). An ingestor acknowledges a range only after ClickHouse accepts it.
**Test app.** `web` (axum, :8081) and `backend` (tonic gRPC, :50051). Endpoints and exact telemetry per request: `/ok` 200, 1 span (web server), 1 INFO log; `/slow?ms=N` 200 after N ms, 1 span, 1 log; `/error` 500, 1 span (status Error), 1 ERROR log; `/exception` 500, 1 span Error with an `exception` span event, 1 ERROR log; `/chain` 200, 4 spans in one trace (web SERVER `GET /chain` -> web CLIENT `backend.Process` -> backend SERVER `backend.Process` -> backend INTERNAL `backend.compute`), 2 INFO logs; `/chain-fail` 502, 3 spans all Error, 2 ERROR logs; `/health` no telemetry. Every response except `/health` carries `x-trace-id`. Each request carries `x-test-run-id`, recorded as attribute `test_run_id`. Metrics: histogram `http.server.request.duration` (s), up-down counter `http.server.active_requests`, counter `app.requests` (attrs service, route, outcome, test_run_id), backend `rpc.server.duration`. Metrics are cumulative and exported every 5 s. Resource attributes include `service.name`, `service.version`, `deployment.environment.name=local`. Context propagation: W3C `traceparent` (HTTP -> gRPC metadata). Logs carry trace id and span id.
**HyperDX.** Sources Logs, Traces, Metrics over the `otel` database. Dashboards *Availability & Latency* (13 tiles) and *Runlog* (4 tiles, filters on `test_run_id`) and four saved searches are created from code through HyperDX's external API v2 (port 8000, Bearer key; limited to 100 requests per window). Availability = non-5xx server spans / total server spans (error status). Alerts: two, `above_exclusive` 4 per 1 m, webhook to a local receiver. HyperDX evaluates alerts once a minute at second :00 over the minute just ended, with no allowance for ingest delay: rows reaching ClickHouse after :00 are not counted. HyperDX's `above` means >=; `above_exclusive` means >. Firing messages read "N exceeds 4" (exclusive) or "N meets or exceeds 4". Cumulative metric charts in HyperDX drop each series' first point, and histogram counts are computed from changes between snapshots. Measured latency (event -> queryable, per row): spans median about 0.6 s, p99 about 4.5 s; logs median about 0.4 s, p99 about 1.3 s (collector flush 100 ms).
**Tests.** `verify.py`: 32 checks in families G (ground truth), A (pipeline: logs, spans, metrics, duplicates), B (tracing), D (HyperDX), E (latency). `selftest.py`: 7 corruptions, all detected. `chaos.py`: scenarios ingestor SIGKILL, ingestor restart, ClickHouse down 20 s, S3 down 8 s and 30 s, garbage entries in all queues, collector restart while idle; every scenario in evidence/chaos.json passes. A separate token-replay probe exists in chaos.py but its output is not captured, so do not quote its result as evidence. `alerts.py`: 11 checks (quiet, boundary of exactly 4 failures must not fire, fire, webhook, resolve; negative tests with unreachable thresholds and with `>=`). Crash replays are timing dependent (the counts in evidence/chaos-ingestor-crash.txt are the only figures to quote).
**Cost model (assumption-heavy).** See module 1 and `evidence/comparison.json`, `evidence/cost-model-output.txt`. Key lever: collector flush interval vs S3 PUT count; at the reference workload a 5 s flush gives about 3.9 million PUTs a month (about $25 of S3 requests), a 0.1 s flush about 194 million (about $1,140), AWS Sydney PUT $0.0055 per 1,000 and GET $0.0044 per 10,000. Log search scanning on the reference bill was 80% of spend. Reference workload: logs 1.59 TB / 2.78 B events per 30 days (569 B each); metrics 485k active series, 7.6k samples/s; Sydney region.
**Emulated amd64.** The 31/31 amd64 run predates the /checkout flow (32 checks now), so say it covers the earlier app.

**Open limits (module 11).** No run on real AWS S3; no load test at production volume (about 1,100 events/s plus 7,600 samples/s); no run on real x86 hardware (amd64 images ran only under emulation: verify 31/31); Go modules of the collector had no supply-chain audit; collector crash loses in-memory batches; a valid value ClickHouse rejects (for example a timestamp past year 2262) is retried forever and blocks that signal's queue; alerts miss late rows; HyperDX external API rate limit; HyperDX's multi-team/RBAC/SSO features unverified; tiers (prod vs non-prod storage and processing, a shared interface on top, environment still carried as an attribute) are a proposal, not built; ClickHouse Cloud rates are unconfirmed and untested. The local stack in `stack/` is the learning and trial environment.

## Quiz gates (check-course.py)

Across the course the right answer may be the strictly longest option in at most 45% of questions, the strictly shortest in at most 40%, and may differ from the other options by more than 20% in length in at most 35%. No correct letter may exceed 42% of questions, no more than two modules may share a sequence of correct letters, and no module may have the right answer as the only shortest (or only longest) option in every question. `ANSWER_AT` in `lib.py` sets where chosen right answers sit.
